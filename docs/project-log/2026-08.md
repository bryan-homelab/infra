# August 2026

## August 25 — Build a separate homelab network

> Reconstructed from `docs/networking/learnings.md` and `docs/networking/overview.md`. Those docs describe this work but do not timestamp every step. This entry is the “story version” of what was already written there, for the state of the lab **before** Ansible on August 26.

### What we were trying to do

The three lab PCs needed their **own private network**, separate from the normal home Wi‑Fi/LAN. At the same time, a MacBook on the home network still needed a way to log into those PCs for management.

### What we set up

1. **Homelab LAN** behind a TP-Link ER605 router  
   - Lab network: `192.168.0.0/24`  
   - Lab gateway (ER605): `192.168.0.1`  
   - ER605’s connection to the home network: `10.0.0.54`

2. **WireGuard VPN** from the Mac to the ER605  
   - Why: the main home router could not be taught a route into `192.168.0.0/24`  
   - VPN addresses: Mac `10.10.10.2`, ER605 `10.10.10.1`  
   - VPN listens on the home side at `10.0.0.54:51820`

In simple terms: the Mac encrypts traffic to the ER605 over the home network; the ER605 decrypts it and forwards it into the lab LAN.

```text
Mac (home Wi‑Fi)
   │
   │  WireGuard tunnel
   ▼
ER605 (10.0.0.54 on home / 192.168.0.1 on lab)
   │
   ▼
Lab PCs on 192.168.0.x
```

### Problem we hit

Early on, a **temporary manual route** on the Mac sent lab traffic toward `10.0.0.54`. That worked for testing, but later WireGuard tried to install its own route for the same lab network and failed with “route already exists.”

**Fix:** look at the Mac routing table, delete the temporary route, then bring WireGuard up again so it owns the lab route.

### Where things stood

- Lab is isolated behind the ER605  
- Mac can reach the nodes through WireGuard (no reverse-SSH hack for day-to-day use)  
- WireGuard private keys stay off Git  

**Next need:** stable IP addresses for each node, then automation (Ansible).

## August 26 — Give nodes stable IPs and start Ansible

### 1. Stable addresses (DHCP reservations)

**Problem:** nodes got IPs from DHCP. After a reboot or reconnect, an address could change. Ansible’s inventory hard-codes IPs, so changing addresses would break automation.

**What we did:** read each machine’s Ethernet MAC address and created **DHCP reservations** on the ER605 so the router always gives the same IP to that MAC.

| Short name | Hostname | Always gets |
| --- | --- | --- |
| node01 | lab-node-01 | `192.168.0.100` |
| node02 | lab-node-02 | `192.168.0.102` |
| node03 | lab-node-03 | `192.168.0.103` |

Also on this network: router `192.168.0.1`, managed switch `192.168.0.2`.

One address we wanted was already taken by something else. We found the conflict and adjusted the reservation before moving on.

**Why reservations instead of setting static IPs on Ubuntu?**  
Same predictable addresses, but the router remains the single place that owns the address plan.

### 2. Ansible inventory + SSH

**Goal:** manage all three Ubuntu machines from the Mac with Ansible.

We created `ansible/inventory/hosts.ini`: a list that maps `node01` / `node02` / `node03` to those reserved IPs, and says “log in as `bryan`.”

Initial connections failed until SSH public-key login was set up from the Mac to each node. After that, Ansible could reach all three.

Mental model:

```text
Mac runs Ansible
  → SSH as bryan (key auth)
    → run modules / playbooks on the node
      → escalate to root only when a task needs it
```

Private SSH keys stay on the Mac, not in this repo.

We confirmed Ansible could connect, run commands, and read system “facts” (hostname, memory, etc.). We added a small playbook, `check-system.yml`, that prints hostname and memory. Ansible warned about an old fact variable style, so the playbook uses `ansible_facts.hostname` / `ansible_facts.memtotal_mb`.

### 3. Big blocker: Ansible + sudo timed out

Installing packages needs root. Ansible’s “become” (sudo) **timed out** waiting for a password prompt.

We checked the obvious things first:

- SSH still worked  
- `bryan` could run `sudo` by hand  
- The password was correct  

Then we noticed Ubuntu 26.04’s `sudo` is actually **sudo-rs** (a different implementation). Ansible’s prompt handling did not work with it. The classic sudo binary is still on the system as **`sudo.ws`**.

**Fix:** add `ansible/ansible.cfg` so Ansible runs `sudo.ws` instead of `sudo`:

```ini
[privilege_escalation]
become_exe = sudo.ws
```

After that, privilege escalation worked. We kept normal password prompts (no passwordless sudo).

**Practical note:** run Ansible commands from inside the `ansible/` directory so this config file is found.

### 4. First real playbook: baseline packages

`playbooks/baseline.yml` declares that these packages should be installed: `git`, `vim`, `unzip`, `tree`, `net-tools`.

- First run: all three nodes reported changes (packages needed installing).  
- Second run: **no changes** — the machines already matched the playbook.

That second result is the point of desired-state config: rerunning is safe and does not keep “reinstalling” everything.

### End of day status

Working:

- Stable IPs via DHCP reservations  
- SSH key login to all nodes  
- Ansible inventory + connectivity  
- Privilege escalation via `sudo.ws`  
- `check-system.yml` and `baseline.yml` applied  

Not done yet:

- Kubernetes is **not** installed  

### Decision for later

When we build the cluster, prefer **kubeadm** over **k3s**. Reason: more of the real Kubernetes bootstrap is visible, which matches the learning goal of this lab. Easier install is less important than understanding the pieces.

**Next phase:** use Ansible to prepare the nodes for kubeadm / Kubernetes.
