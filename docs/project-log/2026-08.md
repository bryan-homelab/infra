# Project Log — August 2026

## August 25 — Homelab Network Foundation

This entry summarizes the networking work documented in `docs/networking/learnings.md` and `docs/networking/overview.md`. That material describes the lab network before Ansible was introduced on August 26. Individual steps are not dated in the repository; this is a reconstruction of what those docs establish as completed.

### Goal

Create a private homelab LAN behind the ER605, separate from the upstream home network, while still allowing secure management access from a MacBook on `10.0.0.0/24`.

### What was built

- ER605 WAN attached to the home network at `10.0.0.54`
- Homelab LAN `192.168.0.0/24` with ER605 as gateway at `192.168.0.1`
- WireGuard management network `10.10.10.0/24` (`ER605` = `10.10.10.1`, Mac = `10.10.10.2`)
- WireGuard endpoint on the ER605 at `10.0.0.54:51820/UDP`
- Split-tunnel access so only homelab destinations go through the VPN

```text
Home (10.0.0.0/24)
        |
   ER605 WAN 10.0.0.54
        |
   Homelab LAN 192.168.0.0/24
        |
   Node 1 / Node 2 / Node 3

Mac ---- WireGuard ----> ER605 (10.10.10.1)
         then routes into the lab LAN
```

### Important problem: route conflict

A temporary static route (`192.168.0.0/24` → `10.0.0.54`) was used early for reachability. When WireGuard came up, `wg-quick` failed with a “route already exists” error because that static route still owned the lab prefix.

**Fix:** inspect the routing table, remove the temporary route, and let WireGuard install the lab route.

### Decision: WireGuard instead of changing the home router

The upstream home router could not be given a route into `192.168.0.0/24`. WireGuard was chosen to create a secure overlay for management without modifying the home router.

### Resulting state

- Homelab is a separate Layer 3 network behind the ER605
- Mac reaches lab nodes through WireGuard + ER605 routing
- Temporary reverse SSH was no longer needed for routine management
- Private WireGuard keys stay off Git

### Next

Stable addressing and configuration management for the three nodes.

## August 26 — Stable Node Addressing + Ansible

### Stable node IP addresses

DHCP leases were shifting after reboot/reconnect, which would break a fixed Ansible inventory. Ethernet MAC addresses were collected and DHCP reservations were configured on the ER605.

| Alias | Hostname | Address |
| --- | --- | --- |
| node01 | lab-node-01 | `192.168.0.100` |
| node02 | lab-node-02 | `192.168.0.102` |
| node03 | lab-node-03 | `192.168.0.103` |

Related LAN addresses: router `192.168.0.1`, managed switch `192.168.0.2`.

One intended address was already in use; the conflict was identified and the reservation/allocation corrected before continuing.

**Why DHCP reservations (not static IPs on the nodes):** predictable addresses for inventory, while address assignment stays centrally managed on the router.

### Ansible introduced

Mac = Ansible control node. Three Ubuntu 26.04 machines = managed hosts.

Created `ansible/inventory/hosts.ini` with a `homelab` group mapping `node01`/`node02`/`node03` to the reserved addresses, and `ansible_user=bryan`.

SSH public-key authentication was configured from the Mac to each node as `bryan`. Private keys remain local and are not in the repo.

```text
Mac
 └─ Ansible over SSH (public-key auth)
     └─ bryan@node0{1,2,3}
         └─ become (when needed) → root
```

Verified connectivity, module execution, ad-hoc commands, and fact gathering. Added `ansible/playbooks/check-system.yml` to print hostname and memory. Updated fact references to `ansible_facts.*` after a deprecation warning about injected fact variables.

### Privilege escalation failure (`sudo-rs`)

Tasks needing root timed out waiting for the privilege-escalation prompt.

Diagnosis:

- SSH worked; `bryan` had sudo; the password worked; interactive `sudo` worked
- Ubuntu 26.04 defaults `sudo` to **sudo-rs**
- Traditional sudo is still available as **`sudo.ws`**
- Failure was Ansible’s interaction with the sudo-rs prompt, not missing privileges

**Fix:** created `ansible/ansible.cfg`:

```ini
[privilege_escalation]
become_exe = sudo.ws
```

Privilege escalation then worked without passwordless sudo. Commands are run from the `ansible/` directory so Ansible picks up this config.

### Baseline playbook

Created `ansible/playbooks/baseline.yml` to ensure packages are present: `git`, `vim`, `unzip`, `tree`, `net-tools`.

First run: `changed=1` on all three nodes. Second run: `changed=0` on all three — confirming idempotency (desired state, safe to rerun).

### Current state

- Privilege escalation via `sudo.ws`
